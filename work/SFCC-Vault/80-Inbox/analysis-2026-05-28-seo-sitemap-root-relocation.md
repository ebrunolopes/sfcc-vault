# Analysis — SEO: Relocate Regional Sitemap Index Files to Root Domain

> Architect-level analysis. Not a TSD. Promote to TSD only after review.
> Inputs: informal requirement doc pasted 2026-05-28.

## 1. Requirement Summary

Six regional sitemap index files (`NORA`, `EUROPE`, `APAC`, `JAPAN`, `MIDDLEEAST`, `INT`) are currently served at locale-prefixed paths (e.g. `/fr_fr/sitemap-EUROPE_custom_sitemap_index.xml`). Search-engine sitemap scope rules require an index file to be at or above the paths it references — a file at `/fr_fr/` lacks authority over `/en_at/`, `/en_au/` etc., all of which appear inside EUROPE's index. The fix is to serve the index files at the domain root while leaving their content untouched.

Acceptance criteria (distilled):

- All six index files respond with 200 OK at `https://www.baccarat.com/sitemap-{REGION}_custom_sitemap_index.xml`.
- `robots.txt` is updated to reference the new root-level URLs — and only after the 200 checks pass.
- The XML content of each index file (entry URLs, `<lastmod>`, `xhtml:link` hreflang tags) is byte-for-byte identical to the current version.
- No change to the individual per-locale/type sitemap files referenced inside the index (e.g. `/fr_fr/sitemap-EUROPE_fr_FR_category.xml` — those stay locale-prefixed).

---

## 2. Technical Feasibility

**Can SFCC do this?** Yes, with a targeted hook.

**Where does this live in the platform?**

| Primitive | Role |
|---|---|
| `onRequest` system hook | Intercept root-level HTTP requests before URL routing, stream IMPEX file directly |
| `dw/io/File` + `dw/io/FileReader` | Read the XML from IMPEX |
| Site preference `RobotsTxtContent` (or cartridge template) | Update `Sitemap:` directives |
| Existing job: `CreateSitemapIndexFile.js` | No change — continues writing `{SITE_ID}_custom_sitemap_index.xml` to `IMPEX/src/sitemaps/` and registering via `SitemapMgr.addCustomSitemapFile()` |

**What's already there to compose with:**

The existing `onRequest.js` at `app_baccarat/cartridge/scripts/middleware/onRequest.js` already has an Apple Pay domain-association handler (lines 46-52) that does exactly this pattern: match `request.httpPath`, read content, write to `response.getWritter()`, return `Status.OK`. Lines 54-58 contain an *incomplete* skeleton for a sitemap intercept — the intent was correct but `file` is undefined and the path pattern is wrong (`"sitemap_index.xml"` instead of the actual filename format).

The index files are generated by `sitemapHelpers.generateCustomSitemapIndexFiles(siteID)` and stored at `IMPEX/src/sitemaps/{SITE_ID}_custom_sitemap_index.xml`. Content is correct — nothing in the generation needs to change.

**Cartridge boundary:** `app_baccarat`. It sits above all regional sites in the cartridge path and its `onRequest` fires for every request on every site.

## 3. Architecture Options

### Option A — Complete the onRequest.js skeleton

**Shape.** Expand the existing 4-line stub in `onRequest.js` into a working sitemap intercept. When `request.httpPath` matches `/sitemap-{REGION}_custom_sitemap_index.xml`, read the corresponding file from `IMPEX/src/sitemaps/{REGION}_custom_sitemap_index.xml`, set `Content-Type: application/xml`, stream it to the response, and short-circuit with `Status.OK`. This runs before any redirect logic, so geolocation and cookie handling are bypassed cleanly — identical to how the Apple Pay handler works.

**Files / touchpoints:**

- `cartridges/app_baccarat/cartridge/scripts/middleware/onRequest.js` — replace lines 54-58 with complete implementation (~20 lines)
- `robots.txt` source (site preference `RobotsTxtContent` or cartridge template — location TBD) — update 6 `Sitemap:` lines

**Effort.** S — skeleton exists, pattern established by Apple Pay handler, ~1 day including QA.

**Pros.**
- Purely SFCC-native, no CDN dependency.
- Uses the exact same pattern already proven by the Apple Pay handler in the same file.
- Files stay in IMPEX — no WebDAV juggling.
- `onRequest` runs in every site context; `IMPEX` is shared, so any site receiving the root-level request will find the file.

**Cons.**
- `onRequest` fires on every request: the regex match is ~0 ns, but an `exists()` + `FileReader` call on a cache miss means disk I/O per sitemap crawl. Sitemaps are rarely requested, so this is negligible in practice but worth documenting.
- Need to confirm `request.httpPath` format for root-level requests — Apple Pay uses a leading slash (`"/.well-known/…"`); the existing stub does not. The implementation must handle both forms or match consistently with how SFCC populates `httpPath` for paths without a locale segment.
- Must determine which SFCC site receives requests to `baccarat.com/sitemap-*.xml` (no locale prefix). All regional sites share the same domain differentiated by locale prefix — root-level paths likely route to a default/INT site or are unrouted (which is fine; `onRequest` still fires).

**Best when.** This is the only site-layer option. Use it unless CDN access is faster to ship.

---

### Option B — CDN rewrite rule (Akamai / Cloudflare)

**Shape.** Add edge rules that transparently forward requests for `/sitemap-{REGION}_custom_sitemap_index.xml` to the existing locale-prefixed origin paths. From the outside (crawlers, robots.txt) these look like root URLs; SFCC never sees the difference.

**Files / touchpoints:**

- CDN configuration (Akamai Property Manager, Cloudflare Rules, etc.)
- `robots.txt` source — update 6 `Sitemap:` lines
- No SFCC code changes

**Effort.** XS–S depending on CDN access and team familiarity with the tooling.

**Pros.**
- Zero SFCC cartridge changes; zero deployment risk.
- Immediately verifiable with curl.
- Serves as a short-term bridge while Option A is built and tested.

**Cons.**
- Infrastructure dependency — requires CDN access and a separate deploy pipeline.
- Doesn't truly relocate the files; creates a proxy alias. Semantically equivalent for SEO but doesn't remove the root cause (the locale-prefixed serving via `SitemapMgr`).
- Per-environment CDN rules maintenance.

**Best when.** Immediate SEO fix is required before the next SFCC deploy window, or if SFCC code deployment is blocked.

---

### Recommendation

**Ship Option A.** The skeleton is already in place — someone on the team identified the right mechanism and got halfway there. Completing it is lower risk than it looks: the Apple Pay handler directly above it proves the pattern works, uses the same `response.getWritter().print()` call, and returns `Status.OK`. The diff is small and contained to a single well-understood file.

If there is a time constraint before the next deploy window, Option B can be shipped as an interim measure with Option A following; the two are not mutually exclusive. CDN rules can be removed once Option A is live.

## 4. Risk & Impact

### Performance

`onRequest` fires on every storefront request. The sitemap pattern match is a single regex against a short string — effectively free. File I/O only triggers when the pattern matches, which happens only when a crawler fetches the index. No N+1, no `SystemObjectMgr` calls. Negligible production impact.

No page-cache implications: sitemap XML should carry `Cache-Control: public, max-age=3600` (or equivalent) so CDN caches aggressively. The response currently set by `SitemapMgr` may already have cache headers — verify and replicate for the new path.

### Security (OWASP frame)

- **Path traversal**: The site ID extracted from the URL must be allowlisted against known values (`NORA`, `EUROPE`, `APAC`, `JAPAN`, `MIDDLEEAST`, `INT`). Do **not** pass raw user input into a file path. Pattern: extract via regex capture group, validate against hardcoded list before constructing the IMPEX path.
- **Output encoding**: XML is served as-is from IMPEX — no ISML rendering, no encoding risk.
- **AuthN/AuthZ**: Sitemaps are public; no auth needed.
- **Input validation surface**: single read-only GET, no POST.

### Accessibility (WCAG 2.1 AA)

No UI components. Not applicable.

### Integration / Cartridge Boundaries

- `SitemapMgr.addCustomSitemapFile()` registration in `CreateSitemapIndexFile.js` continues unchanged. The locale-prefixed URLs remain valid — Option A adds a *new* root-level path, not a replacement. Old locale-prefixed URLs will continue to serve until `robots.txt` is updated.
- No Adyen, Algolia, or other third-party cartridge involvement.
- `app_baccarat` is the top-level cartridge for all regional sites, so the `onRequest` change is universal. There is no per-site override risk.

### Observability

- Add a `Logger.info("[onRequest] Serving sitemap index: {0}", fileName)` line inside the intercept so production logs confirm the new path is being hit before robots.txt is updated.
- No new log category needed; existing `onRequest` log context is sufficient.

### Testing Strategy

- **Unit**: mock `request.httpPath` with each of the 6 region patterns and one non-matching path; assert correct file read and early return.
- **Integration**: deploy to sandbox, curl each of the 6 root-level URLs, verify: 200 status, `Content-Type: application/xml`, XML content matches the current locale-prefixed equivalents byte-for-byte.
- **Manual QA**: confirm robots.txt reflects new URLs; submit updated sitemap URLs to Google Search Console and verify indexing picks up the change.

### Deprecation / Debt

The existing stub at lines 54-58 of `onRequest.js` has an undefined `file` reference — it would throw a `ReferenceError` if the path `"sitemap_index.xml"` were ever matched. Replace it entirely as part of this work; don't leave dead code.

- [ ] **Where is the `Sitemap:` content in robots.txt defined?** Is it in the `RobotsTxtContent` site preference, a content asset, or a cartridge template? The robots.txt update cannot be scoped until this is confirmed.
- [ ] **Are 301 redirects from old locale-prefixed index URLs to new root URLs required?** Good practice for SEO link-equity continuity; not in the stated requirements but worth confirming with SEO stakeholder.
- [ ] **Is CDN caching configured for sitemap responses?** If the current locale-prefixed responses are CDN-cached with long TTLs, the new root paths may return stale/empty until cache is purged or TTL expires.

## 6. Contradictions / Red Flags

- The requirement says "don't change the content" while also implying the robots.txt must change. These are different files — no contradiction, but worth calling out: *the index files' XML content* is frozen; *robots.txt* and the serving path are what change.
- The existing stub at `onRequest.js:54` checks for `"sitemap_index.xml"` — this pattern never matches any real request (no SFCC URL produces this path), so it is dead code. The intent was the right mechanism; the implementation was abandoned mid-way. Flag for cleanup in the same PR.
